# 1-2 · 구조

상세 절차는 `docs/01-stage-analysis.md`의 1-2 항목. 읽고 시작한다.

입력은 `00-brief.md`, 채우는 파일은 `01-ui-structure.md`.

## 시작 전에

`00-brief.md`의 전략이나 리스크, 화면 후보가 비어 있으면 `ui-analyze`를 먼저 부른다. 사용자가 구조를 말로 이미 정해줬으면 그걸 입력으로 쓴다.

## 순서

### 1. 사이트 유형

`docs/01-stage-analysis.md`의 여덟 가지 유형 중 제일 가까운 걸 고른다. 기획서가 여러 유형 특성을 섞어서 요구하면 억지로 하나에 끼워 맞추지 말고 하이브리드로 제안한다.

검토했는데 제외한 유형이랑 이유도 적는다. 나중에 반드시 질문이 나온다.

### 2. IA 트리

3뎁스를 넘기지 않는다. 페이지마다 한 줄로 목적을 붙인다.

### 3. 화면 목록 표

`상태 변형` 칸을 꼭 채운다. 빈 상태, 로딩, 에러, 권한 없음처럼 추가로 그려야 하는 화면이다.

표를 채운 뒤 두 숫자를 계산해서 보여준다.

```
명목 화면 수: n개
실제 화면 수(변형 포함): m개
```

보통 m이 n의 1.3~1.6배로 나온다. 이 숫자가 일정의 근거가 되니까 사용자에게 명시적으로 알린다.

### 4. 레이아웃 3안

등급 정의는 `docs/reference-rules.md`의 세로축 표를 따른다.

안마다 이걸 쓴다.
- 존 순서 (번호 목록)
- 그리드 값. 칼럼, 거터, 최대폭, 브레이크포인트
- 근거 레퍼런스. 레이아웃 근거는 실제 운영 사이트에서만 가져온다. 컨셉 샷은 쓰지 않는다 (`docs/reference-rules.md`)
- 장점이랑 트레이드오프
- 파격 안은 리스크까지

A·B·C로 부르지 않는다. A급/B급 시안이랑 헷갈리니까 정석·변주·파격으로 쓴다.

기획서에 다른 값이 없으면 기본 그리드는 이걸 쓴다.
```
데스크톱 1440 / 콘텐츠 최대폭 1200 / 12칼럼 / 거터 24
태블릿 768 / 8칼럼      모바일 375 / 4칼럼
```

### 5. 보여주기

3안을 나란히 비교할 수 있게 보여주고 하나를 추천한다. 추천 없이 세 개만 늘어놓으면 고르는 시간만 길어진다.

### 6. 고르게 하고 다음으로

사용자가 하나를 고르면 `01-ui-structure.md`의 `확정` 표에 날짜랑 결정자를 적는다. 고객 컨펌 전이면 `내부 확정: 고객 대기`로 표시한다.

그리고 "스타일 방향(1-3)으로 넘어갈까요?" 하고 묻는다. 동의하면 `ui-style`을 부른다.

## 주의

- 여기서 컬러나 폰트, 톤을 다루지 않는다. `ui-style` 일이다.
- 안을 세 개보다 늘리지 않는다.
- 화면 목록에 없는 화면을 시안에서 만들지 않는다. 필요하면 이 파일부터 고친다.
