# 1-1 · 분석

상세 절차는 `docs/01-stage-analysis.md`의 1-1 항목에 있다. 읽고 시작한다. 이 파일에는 실행 순서만 둔다.

채우는 파일: `projects/[프로젝트명]/00-brief.md`

## 시작 전에

`00-brief.md`의 기본정보 표가 비어 있으면 `ui-intake`를 먼저 부른다.

## 순서

### 1. 문서 전문 읽기

`source/`의 문서를 형식에 맞는 스킬로 읽는다(pdf / docx / pptx). 요약본 말고 전문을 읽는다. 표랑 각주에 제약 조건이 숨어 있는 경우가 많다.

### 2. 여섯 가지 뽑기

`docs/01-stage-analysis.md`의 여섯 항목을 순서대로 뽑는다. 특히 두 가지는 대충 넘기지 않는다.

- **5번 디자이너가 챙겨야 할 것** — 문서의 체크 항목 열 개 표를 그대로 훑는다. 해당하는 것만 근거(문서 위치)와 같이 적는다.
- **6번 문서에 없는 것** — 이 단계에서 제일 값나가는 산출물이다. 요약보다 여기에 시간을 쓴다.

모든 항목에 출처(문서 몇 쪽, 어느 섹션)를 붙인다. 출처가 없으면 `추정` 표시를 한다.

### 3. 전략 한 줄, 리스크 세 개

```
이 프로젝트의 디자인은 ______ 로 승부한다.
```

근거는 기획서에서 가져온다. 근거를 못 대면 그건 전략이 아니라 취향이다.

리스크는 각각 `이게 터지면 무슨 일이 생기는가`랑 `어떻게 대응하나`까지 쓴다.

### 4. 확인 질문 목록

3~7개. 질문마다 `누구에게` `언제까지`를 붙인다.

여덟 개를 넘으면 그 사실을 사용자에게 먼저 말한다. 기획서가 아직 디자인을 시작할 상태가 아니라는 뜻이다.

### 5. 결과 보여주고 다음으로

`00-brief.md`를 채운 뒤 화면에는 아래만 요약해서 보여준다.
- 전략 한 줄
- 리스크 세 개
- 확인 질문 목록

그리고 "구조(1-2)로 넘어갈까요?" 하고 묻는다. 동의하면 `ui-structure`를 부른다.

## 주의

- AI 요약을 최종본으로 내지 않는다. 숫자랑 고유명사는 원문 대조를 거친 것만 확정으로 쓴다.
- 기획서에 없는 업계 관행을 문서 내용인 것처럼 쓰지 않는다. `docs/00-principles.md`의 관련 항목을 보라.
- 여기서 구조나 스타일 제안을 시작하지 않는다. 다음 스킬 일이다.
