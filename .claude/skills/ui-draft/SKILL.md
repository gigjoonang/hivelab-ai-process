# 2-1 · 시안

상세는 `docs/02-stage-build.md`의 2-1 항목, 명명 규칙은 `docs/design-system-rules.md`, 합격 기준은 `docs/quality-bar.md`. 셋 다 읽고 시작한다.

입력은 `01-ui-structure.md`, `02-design-style.md`, `03-design-tokens.md`. 채우는 파일은 `04-draft-log.md`.

여기서 만드는 건 B급 시안이다. 방향 비교용 초안이고 고객사에 그대로 가지 않는다. 결과를 공유할 때마다 이 얘기를 한다.

## 시작 전에

1. **방향 확정** — `01-ui-structure.md`, `02-design-style.md`의 확정 표가 채워져 있나. 비었으면 멈춘다.
2. **토큰** — `03-design-tokens.md`가 채워져 있나. 비었으면 `ui-tokens`를 먼저 부른다.
3. **스크린샷** — HTML을 PNG로 캡처할 수 있나. 헤드리스 브라우저가 있는지, Bash로 설치할 수 있는지, 아니면 이 세션의 브라우저 도구를 쓸 수 있는지 확인한다.
4. **Figma 연결** — `mcp__TalkToFigma__*` 툴을 지금 쓸 수 있나. 없으면 안내한다.
   > "Figma에서 대상 파일을 열고 TalkToFigma 플러그인을 실행한 다음, 화면에 뜨는 채널 이름을 알려주세요."
   채널 이름을 받으면 `join_channel`로 접속한다.
   Figma Dev Mode MCP 툴이 따로 있으면 그건 읽기 전용이다. 기존 시스템 참고에만 쓰고 생성이나 수정은 전부 TalkToFigma로 한다.

Figma 연결이 없어도 HTML 시안은 먼저 만든다. 연결 기다리면서 놀지 않는다.

## 순서

### a. 디자인 컨셉

```
[대상]에게 [무엇]을 [어떤 방식]으로 보여주는 화면
```

형용사가 두 개 이상이면 컨셉이 아니라 희망사항이다. 다시 쓴다.

컨셉에서 디자인 규칙 세 개를 뽑는다. 시안 만들다 판단이 갈릴 때 이걸로 결정한다.

### b. 컴포넌트 설계

나중에 편집이 편한 시안이 되느냐가 여기서 갈린다. 화면 먼저 그리고 나중에 묶으면 안 묶이는 조각이 꼭 남는다.

`01-ui-structure.md`의 화면 목록을 훑어서 두 번 이상 반복되는 요소를 전부 올린다. 기본 세트(Button, Input, Card, Badge, Header, Footer, NavItem, Modal, Toast, Icon)에 프로젝트 전용을 더한다.

명명은 `docs/design-system-rules.md`를 따른다. variant를 쓰고 컴포넌트를 복제하지 않는다.

목록을 `04-draft-log.md`에 적고 넘어간다.

### c. HTML 시안 먼저

Figma에 바로 그리지 않는다. Figma를 자동으로 조작하는 도구는 사각형, 텍스트, 단색 채우기 정도밖에 못 한다. 말로 된 설명만 보고 좌표를 추측해 그리면 엉성하게 나온다. HTML/CSS로 타이포랑 여백, 대비를 제대로 잡은 화면을 먼저 만들어놓고 그걸 보면서 옮긴다.

- `projects/[프로젝트명]/drafts/draft-[방향].html`
- `03-design-tokens.md` 값을 CSS 변수로 선언하고 그것만 쓴다. 하드코딩 색상 없음
- 존 순서는 `01-ui-structure.md`의 확정 레이아웃 그대로
- 카피는 기획서의 실제 문구 후보를 쓴다. 없으면 무슨 역할인지 알 수 있는 국문 자리표시 문구. `Lorem ipsum`은 쓰지 않는다. 국문이랑 길이감이 완전히 달라서 레이아웃 판단이 안 된다
- 제일 긴 경우랑 제일 짧은 경우를 한 번씩 확인한다
- 데스크톱 폭으로 PNG 캡처. `drafts/draft-[방향].png`

캡처를 사용자에게 먼저 보여주고 확인받는다. "이 방향으로 Figma에 옮길까요?" 사용자가 이미 "확인 없이 끝까지"라고 했으면 묻지 말고 넘어간다.

### d. Figma 이관

HTML 캡처를 보면서 옮긴다. 말로 된 설명이 아니라 이미지를 보고 좌표랑 크기, 색을 옮긴다.

1. `get_document_info`, `get_local_components`, `get_styles`로 기존 파일을 본다. 재사용할 컴포넌트가 있으면 새로 만들지 말고 `create_component_instance`로 배치한다
2. 토큰을 Figma에 올린다. 컬러/텍스트 스타일이나 변수로
3. b에서 정한 컴포넌트를 컴포넌트로 먼저 만든다
4. `create_frame`으로 최상위 프레임. 데스크톱 폭, `layoutMode: VERTICAL`, 배경은 `color/bg-default`
5. 섹션별 하위 프레임을 오토레이아웃으로 만들고 컴포넌트 인스턴스를 배치해서 채운다. `set_layout_mode`, `set_item_spacing`, `set_padding`으로 정렬을 맞춘다
6. 이미지 자리는 `create_rectangle` 플레이스홀더에 이름으로 규격 표기. `ph_hero-bg_2880x1620`
7. 프레임 이름은 `화면ID_화면명_B_방향`

폰트 얘기: TalkToFigma의 텍스트 생성은 폰트 패밀리를 직접 지정하지 못한다. `get_styles`에서 찾은 기존 텍스트 스타일 중 HTML 시안 서체랑 제일 가까운 걸(굵기감, 세리프 여부, 전체 인상) 고른다. 빈 파일이면 기본 폰트로 진행하고 마지막에 고지한다.

### e. 점검하고 공유

`docs/quality-bar.md`의 A부터 H까지 전부 점검하고 결과를 `04-draft-log.md`에 적는다. F 구간(편집 가능성)은 예외 없이 통과해야 한다.

`export_node_as_image`로 Figma 결과를 캡처해서 HTML 원본이랑 나란히 보여준다.

공유할 때 매번 같이 말한다.
- 이건 B급(비교용) 시안이다
- 어느 구조안에 어느 스타일 방향 조합인가
- 폰트가 의도랑 다를 수 있다. 제일 가까운 기존 스타일로 대체됐다
- 사진은 색상 플레이스홀더다
- 그라데이션이랑 그림자는 단순화됐다

### f. 여러 방향 비교

같은 구조에 방향이 여럿이면 프레임을 `x` 좌표로 나란히 배치해서 한 화면에서 비교하게 만든다. 이때 HTML 시안도 방향별로 각각 만든다.

## 피드백 반영

전체를 다시 만들지 않는다. `move_node`, `set_fill_color`, `set_text_content` / `set_multiple_text_contents`, `clone_node`로 해당 부분만 고친다.

컨셉이나 방향 자체를 바꾸는 큰 피드백이면 a부터 다시 돈다.
토큰이 문제면 시안에서 고치지 말고 `ui-tokens`로 돌아간다.

## 주의

- Figma 연결이 안 되면 무리해서 다른 방법으로 대체하지 않는다. 연결 상태를 알리고 안내를 준다.
- 기존 디자인 시스템이 있으면 새로 만들기보다 재사용을 우선한다.
- 품질 기준을 낮춰서 통과시키지 않는다. 일정이 급하면 시안 개수를 줄인다.
